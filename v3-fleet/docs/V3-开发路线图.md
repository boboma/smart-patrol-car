## 0. 版本策略与总原则

| 版本 | 内容 | 状态 |
|---|---|---|
| V1 | TCP 直连（lab01-tcp-sim） | 定版归档，不动 |
| V2 | IoT 云控单车版（iot-stage） | **定版冻结**，作为教学版本 |
| V3 | 车队版（v3-fleet，本工程） | 开发中 |

**总原则：**
1. V3 是从 V2 复制出来的独立工程，版本间文件互不影响
2. 第 ①~⑦ 步**全部使用模拟车开发，不依赖真车**——真车何时到货不影响进度
3. 真车已到货（2026-11-07，润开鸿 HH-TERE-W10）：按马老师定的口径，以 V2 为基准在**独立工程 `v1-car` / `v2-car`** 调试，V2 不支持退 V1，需改代码一律拷贝原工程再改，不动任何定版。该硬件线**不回改 V3**，独立于 V3 软件开发
4. 云侧（IoTDA 物模型、MQTT 协议、应用侧 SDK）零改动，只改业务层
5. 硬约束：IoTDA S0 免费单元每日约 1 万条消息，设备端上报节奏（运动 5s/空闲 60s）不随意调快

## ① 多车模拟底座

**目标**：云端同时有两台以上模拟设备在线上报，为后续所有多车改造提供测试数据源。

**具体工作**：
1. 创建 V3 工程骨架 `v3-fleet/`：`server/`、`device/`、`web/`、`docs/`（从 V2 复制改造，不共用文件）
2. 设备注册表 `server/devices.json`：静态登记 car_001 / car_002（device_id、名称、渲染色）
3. 设备端模拟器迁移至 `device/`，双实例同时运行（car_mqtt_client_001 / 002 已在 V2 验证过，主要是收编进 V3 工程）
4. 验证双车影子同时更新、互不串扰

**产出物**：v3-fleet 工程骨架、devices.json、双车模拟器启动脚本、README

**验收标准**：双实例同时连 MQTT，控制台/影子查询能看到两台设备各自独立的位置数据

## ② 业务后端多车化

**目标**：业务后端从"写死单台"升级为"按设备注册表路由"，接口与协议文档 v1.0 完全对齐。

**具体工作**（对照协议文档第 4 节）：
1. 加载 devices.json 为设备注册表（启动时校验 device_id 格式）
2. `GET /devices`：车列表 + 在线状态 + battery（新增）
3. `GET /status?device_id=`：device_id 必填，未注册返回 400（改造）
4. `POST /command`：body 加 device_id 必填，命令路由到对应设备（改造）
5. `GET /fleet/status`：一次返回全部车状态（新增）
6. `GET /health`：返回车队摘要 total/online（改造）
7. 审计日志 commands.log 增加 device_id 字段
8. 后端内部增加"车队状态缓存"模块（内存 dict：device_id → 最新状态），为 ④ 的 WebSocket 广播打底

**产出物**：V3 版 app.py、devices.json 校验逻辑、接口自测脚本

**验收标准**：用 curl 对两台车分别完成 查列表 → 查状态 → 下发命令 全流程；未注册的 device_id 返回 400

## ③ 轨迹落库与回放

**目标**：位置数据从"看完即丢"变为可持久化、可回查。

**具体工作**：
1. SQLite 表设计：`track_points(device_id, x, y, heading, speed, battery, ts)`
2. 影子刷新时自动插行（挂在状态缓存更新处）
3. `GET /track?device_id=&from=&to=`：按时间窗查轨迹点（协议文档第 7.3 节）
4. 简单数据治理：单车上限条数 / 按天清理策略（防 SQLite 无限膨胀）

**产出物**：SQLite 库文件、/track 接口、建表与清理脚本

**验收标准**：双车跑动 10 分钟后，/track 能查到两车各自完整的轨迹点序列

## ④ 网页端多车渲染

**目标**：网页从"单车 2 秒轮询"升级为"多车 WebSocket 实时分轨渲染"。

**具体工作**（对照协议文档第 7 节）：
1. 后端加 `WebSocket /ws`：每 1 秒广播 `fleet_state` 帧（数据源 = ②的状态缓存），心跳 ping/pong
2. 网页端多车分轨：每车独立颜色（读 devices.json 的 color）与轨迹
3. 车辆选择器：勾选显示哪几辆 / 单车跟随视角
4. 轨迹回放页：选车 + 时间窗，调 /track 拉历史点动画回放
5. 断线指数退避重连（复用 V1 car_view 成熟代码）

**产出物**：V3 版 web 页面（实时监控 + 回放两视图）

**验收标准**：双车同屏分轨实时显示；控制某车移动，网页 5 秒内看到位置变化；回放页能重现历史轨迹

## ⑤ B/S 管理后台

**目标**：把监控页面扩展为完整管理后台，覆盖"设备管理 + 运营数据"。

**具体工作**：
1. 设备管理页：设备列表 / 注册新设备（写 devices.json + 调云端注册）/ 冻结解冻
2. 命令历史页：commands.log 结构化展示（谁、何时、对哪台车、发了什么、结果）
3. 车队总览页：在线/离线统计、电量排行、消息量统计（为额度监控打底）
4. 简单登录保护（教学环境，单管理员账号即可）

**产出物**：管理后台（监控/设备/命令/总览四页）

**验收标准**：后台完成一次完整"注册模拟设备 → 控制 → 查历史 → 冻结"闭环

## ⑥ APP 多车关联

**目标**：鸿蒙 APP 从"控一辆固定车"升级为"选车绑定 + 控制指定车"。

**具体工作**：
1. 新建 V3 APP 工程（复制 CarCtrlCloud，改 bundle 名）
2. 选车页：调 `GET /devices` 列车列表（名称/在线/电量），点选绑定
3. 控制页：所有请求带 device_id（`GET /status?device_id=`、`POST /command`）
4. 端侧 Preferences 记住上次绑定的车（决策 D2），下次启动自动恢复
5. 切车入口：控制页可随时返回选车页换车

**产出物**：V3 版鸿蒙 APP（可跑模拟器）

**验收标准**：模拟器里完成"选 car_001 控制 → 切到 car_002 控制 → 重启 APP 自动恢复上次绑定"全流程

## ⑦ AI 增强

**目标**：给车队加 AI 大脑，形成演示爆点。

**具体工作**：
1. 自然语言控车：后端加 `POST /ai/command`，LLM 把"去 3 号楼看看"解析为目标点 + 命令序列，经既有 /command 链路执行并返回步骤反馈
2. 巡检报告生成：按车汇总当日轨迹 + 命令历史，LLM 生成文字版"巡检日报"
3. （可选进阶）多车任务调度：任务点分配给最近的车
4. LLM 接入走可配置 API（中转站 base_url + key 存配置文件，不入库不入仓）

**产出物**：/ai/command 接口、APP/网页的对话入口、巡检报告页

**验收标准**：一句自然语言能驱动指定车完成一组动作并播报执行结果；一键生成当日巡检报告

## ⑧ 真车接入（硬件调试线，独立于 V3 软件开发）

> 口径（马老师 2026-11-07 定）：真车已到货。以 V2 为基准调试 → V2 不支持退 V1 → 需改代码则拷贝原工程命名 `v1-car` / `v2-car` 再改，不动定版；不回改 V3。下方 1~5 为原定实施要点，实际路径待厂商固件源码 / 串口命令表确认后调整。

**目标**：真车作为 V3 多车架构中的一台设备跑通，全链路验收。

**具体工作**：
1. 真车主控烧写设备端程序（对齐 V2 已验证的 MQTT 协议，device_id 用真实注册设备）
2. 电机/传感器联调：命令响应、位置上报真实性校准
3. 断线重连、命令超时、弱网表现的异常路径测试
4. 端到端延迟实测（APP → 后端 → 云 → 车 → 影子 → 网页），对照 D3 的 5 秒预期
5. 演示场景编排：多模拟车 + 1 真车同屏，AI 控真车完成一次巡检

**产出物**：真车设备端固件、联调记录、期末演示场景

**验收标准**：真车在 V3 后台与网页中与其他模拟车同屏受控，全链路稳定运行 30 分钟
